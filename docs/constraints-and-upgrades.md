## 1 · 渲染管线与分辨率

### 1.1 GPU 档位只有「核显 / 独显」两档，且靠 GPU 名字正则猜
**现状**（`src/02-scene.js:34`）
```js
export const GPU_TIER = GPU_TIER_FORCED || (/Intel|Iris|UHD Graphics|HD Graphics|Radeon\(TM\) Graphics|Vega|llvmpipe|SwiftShader/i.test(GPU_NAME) ? 'low' : 'high');
```
只有 `low` / `high` 两个值。命中关键词 → low（关 AO、关体积光、关平面反射、阴影 2048）；否则 high（全开、阴影 6144）。

**为什么要这么设**：`02-scene.js:8-11` 注释写明——双显卡笔记本浏览器常跑在核显上（实测 Intel Iris Xe 只有 22.6fps，同场景 RTX 4060 是 54.3fps）。两档是最省事的"能跑/不能跑"分流。

**问题**：
- 中间设备（Apple M 系、Intel Arc、老独显）**要么吃满要么砍太狠**，没有中间态；
- 正则只看名字——**iPad / Apple Silicon 可能被误判成 high**（`optimization-plan.md` Phase 0 已把它列为待查项）；
- `llvmpipe/SwiftShader` 也被归进 low，与真核显混在一起（探针环境与真机同档）。

**松绑方案**：
- **A. 三档细分**（low / mid / high）：mid 档保留 AO 但关平面反射、阴影 4096。
- **B. 主动探测替代正则**：读 `WEBGL_debug_renderer_info` + `gl.getParameter(MAX_TEXTURE_SIZE)` + 可选一次 30 帧微基准（跑一个小场景测真实帧率），按实测分档。
- **C. 手动覆盖**：`?tier=mid` 已支持（`02-scene.js:33`），可加进 UI。

**好处**：中端设备不再"要么卡要么丑"；iPad 不再被误判；档位与真实能力对齐。

**代价**：时间 **0.5~1 人日**（改判档 + 三档参数表 + 跑门禁）｜付费 **0**｜硬件要求 **不升**（这是更聪明的适配，不抬高最低门槛）。

### 1.2 超采样从 1.5× 砍到 1.15×
**现状**（`src/02-scene.js:40`）
```js
export const SUPERSAMPLE = GPU_TIER === 'low' ? 1.0 : 1.15;   // 原 1.5 → 2.25 倍像素面积太烧（用户实测掉帧到十几帧）
```
超采样（SSAA）= 用高于屏幕的分辨率渲染再缩回来，是**竹林叶片 / 窗棂 / 瓦垄**这类高频细节最有效的抗锯齿。从 1.5 降到 1.15，等于放弃了一半以上的像素面积。

**为什么要这么设**：1.5× 是 2.25 倍像素面积，用户实测掉到十几帧。

**松绑方案**：
- **A. TAA（时间性抗锯齿）**：把多帧的历史信息累积起来抗锯齿，**画质接近 1.5× SSAA，但开销远低于它**（每帧只多一个 resolve pass + 历史缓冲）。
- **B. SMAA / FXAA 后处理**：最便宜，但会糊细节（对瓦垄这种细密纹理是负优化）。
- **C. 动态超采样**：帧率 > 58 时自动提到 1.35，掉了自动回 1.15（复用现有 QOS 的帧率采样）。
- **D. 渐进式超采样**：**只在相机静止时**逐帧累积更高采样（动起来立刻回 1.15）——拍照/明信片场景最受益。

**好处**：静态画面边缘干净度接近 1.5×；移动时又不掉帧。

**代价**：TAA **2~3 人日**（实现 + 鬼影调参，枝叶高速摆动时容易拖影，是主要难点）｜SMAA/FXAA **0.5 人日**（但效果打折）｜动态/渐进超采样 **1 人日**（复用 QOS，风险最低）｜付费 **0**｜硬件：TAA 在中端 GPU 上开销 < SSAA 1.5×，**反而降低门槛**。

### 1.3 像素预算封顶 1440p
**现状**（`src/02-scene.js:45-48`）
```js
const PIXEL_BUDGET = GPU_TIER === 'low' ? 1920*1080*1.1 : 2560*1440*1.05;   // 原 3840*2160*1.05：高 DPR/大屏上 2.25× 像素把帧率拖到 10-20
export const RENDER_SCALE = Math.min(Math.max(devicePixelRatio, SUPERSAMPLE),
  Math.max(1, Math.sqrt(PIXEL_BUDGET / Math.max(1, innerWidth*innerHeight))));
```
4K / 高 DPR 屏被压回原生甚至更低。

**为什么要这么设**：4K×1.05 预算在高 DPR 屏上把帧率拖到 10-20。

**松绑方案**：
- **A. 按档位给不同预算**：high 档开放到 4K（3840×2160×1.05），low 保持 1080p。
- **B. 动态分辨率（DRS）**：**按实时帧率连续调 scale**，而不是一个固定上限——高配机吃满 4K，卡了自动降，不卡就升。

**好处**：高配机真正吃满 4K；低配机自动兜底，不用手动改参数。

**代价**：A **0.3 人日**（改一个常量）｜B **1~2 人日**（DRS 与 QOS 要合并设计，否则两套分辨率逻辑打架）｜付费 **0**｜硬件：高预算只在 high 档开放，最低门槛不变。

### 1.4 QOS 只有 4 档，且档位跳变大
**现状**（`src/11-loop.js:500-505`）
```js
const LEVELS = [
  { scale: 1.00, ao: true,  shadow: 6144 },   // L0
  { scale: 1.00, ao: false, shadow: 6144 },   // L1 关 AO
  { scale: 0.85, ao: false, shadow: 2048 },   // L2 降分辨率 + 降阴影
  { scale: 0.72, ao: false, shadow: 1024 },   // L3
];
```
降档：连续 6 窗口（≈3s）< 45fps；升档：12 窗口 > 58fps。

**为什么要这么设**：带滞回的服务质量控制，防止阈值附近抖动。

**问题**：L1→L2 **同时**降分辨率和阴影，可能"一步丑太多"；档位粒度粗。

**松绑方案**：把 `scale` / `shadow` / `ao` 三个旋钮**各自独立滞回**，或增加中间档（如 L1.5 只降阴影不降分辨率）。

**好处**：画质随帧率平滑退化，不会一步掉档太狠。

**代价**：**1 人日** + 回归（smoke 已断言降档 ×0.72 与升回 L0，改逻辑要同步改断言）｜付费 **0**｜硬件不变。

## 2 · 光影与后处理

### 2.1 阴影图 6144²，8192² 被否
**现状**（`src/09-lights.js:116-119`）
```js
// 8192² 的阴影填充代价偏高（实测挤占了帧预算），退到 6144²
sun.shadow.mapSize.set(GPU_TIER === 'low' ? 2048 : 6144, ...);
```
texel 密度 ≈ 110 texel/m。

**为什么要这么设**：8192² 填充代价太高（6144²≈3770 万纹素的深度图）。

**松绑方案**：
- **A. 级联阴影 CSM（Cascaded Shadow Maps）**：把视锥切成几段，近处用高分辨率、远处用低分辨率——**近观阴影精度可翻倍而不增总开销**。
- **B. high 档直接上 8192²**：最简单，但显存吃紧。
- **C. 视距自适应**：相机拉近时只重渲局部高精度阴影。

**好处**：近观（窗棂投影、栏杆投影、假山石缝阴影）清晰很多。

**代价**：CSM **3~4 人日**（Three.js 无内置，需引 addon 或自写 + 与现有 `fitShadowCamera` 自动拟合盒（`09-lights.js:164`）整合）｜8192² **0.5 人日**，但显存 8192²×深度 ≈ **256MB+**，需 ≥4GB 显存余量 ｜付费 **0**。

### 2.2 点光源完全不投影
**现状**（`src/12-env.js:287-301`）
```js
// ⚠️ castShadow 一律 false：PointLight 的阴影是 6 面立方体贴图，一盏顶六盏平行光，
//    原来堂前两盏开着它 = 每帧多渲 12 张深度图，纯亏不赚。
const spot = new THREE.PointLight(0xFFAA33, 0, isHall ? 8.0 : 5.0, 2.0);
spot.castShadow = false;
```

**为什么要这么设**：点光阴影 = 立方体贴图 = 6 张深度图/盏，5 盏灯 = 30 张，代价不可接受。

**松绑方案**：**改用 SpotLight**（向下打光只需 1 张深度图）——灯笼本来就是往下照地面，用聚光灯更贴物理，且阴影成本从 6 张降到 1 张。

**好处**：夜间灯笼投出影子，光影更立体（现在夜里灯笼只照亮、不投影，略平）。

**代价**：**0.5 人日**（换光源类型 + 调锥角/衰减）｜付费 **0**｜硬件：5 盏 × 1 张 = 5 张深度图，中端可承受，核显需在 low 档关。

### 2.3 GTAO 全分辨率 + 32 采样
**现状**（`src/10-post.js:63,72`）
```js
const gtao = new GTAOPass(scene, camera, innerWidth, innerHeight);   // 全尺寸
gtao.updateGtaoMaterial({ radius: 1.8, samples: 32 });               // PC 端直接拉满
```
GTAO（环境光遮蔽）= 在构件与地面接触处压暗角，治"构件像浮在地面上"。代价是**法线 pass 要把场景几何再画一遍**（draw call / 三角形各翻一倍）。

**为什么要这么设**：PC 端拉满质量，小视口（移动端）直接不接这个 pass。

**松绑方案**：**半分辨率 GTAO + 时间性去噪**（`optimization-plan.md` 未做项 1）。AO 是低频信号，半分辨率肉眼看不出差别。

**好处**：AO 成本减半，省下的预算可给阴影 / 反射。

**代价**：**1~2 人日**。⚠️ **已知坑**（`optimization-plan.md` 实证提示 ①）：**收益可能被 QOS 的 L1（关 AO）吃掉**——设备一旦掉档就整个关掉 AO，半分辨率省下的成本根本用不上。**应先看 Phase 0 档位判定再决定做不做**。｜付费 **0**｜硬件不变。

### 2.4 环境贴图（PMREM）只在启动烘一次
**现状**（`src/02-scene.js:287-305`）
```js
scene.environment = pmrem.fromScene(es, 0.035).texture;   // 只烘这一次
// 之后不重烘、只按「当前天光亮度 / 烘焙时天光亮度」缩放它（lumOf / ENV_BAKE_LUM）
```

**为什么要这么设**：重烘一次 PMREM 有几十毫秒卡顿；用缩放代替重烘，代价只是一个标量。

**问题（这是真实的"合理性"缺陷）**：夜间 / 阴天材质**仍被"白天"的环境光照着，只是整体变暗**——石头的反射色是白天的蓝天，不是夜里的月光冷色。金属 / 水面 / 石材的**反射色随时段是错的**。

**松绑方案**：按时段 / 天气**重烘 PMREM**，但要**节流**——只在环境过渡结束时烘一次（不要每帧）；或用更便宜的实时天空探针（CubeCamera 降频更新）。

**好处**：金属 / 水面 / 石材的反射色随时段正确（夜里反射月光冷色、黄昏反射暖橙）。

**代价**：**2 人日**（重烘时机 + 节流 + 避免过渡期卡顿）｜付费 **0**｜硬件：GPU 上可接受，核显需降频或跳过。

### 2.5 抗锯齿只有 MSAA 4×（无后处理 AA）
**现状**（`src/10-post.js:14`）
```js
const composerTarget = new THREE.WebGLRenderTarget(1, 1, { type: THREE.HalfFloatType, samples: 4 });
```
后处理链是 RenderPass → GTAO → bloom → grade → output，**没有 SMAA/FXAA/TAA**。走 EffectComposer 时 `renderer` 的 `antialias` 会被完全绕过（注释 `10-post.js:12-13` 写明），所以全靠 MSAA 4× + SSAA 1.15。

**松绑方案**：加一道 **SMAA**（比 MSAA 更擅长处理细密几何的走样）或 **TAA**（见 1.2）。两者可叠加 MSAA 使用。

**好处**：竹林叶片、窗棂这类"细到一像素"的几何边缘更稳。

**代价**：SMAA **0.5 人日**｜TAA **2~3 人日**（与 1.2 是同一件事）｜付费 **0**｜硬件：SMAA 极轻，TAA 中等。

### 2.6 雾是全局指数雾（FogExp2），无体积雾
**现状**（`src/02-scene.js:62`）
```js
scene.fog = new THREE.FogExp2(CFG.fog.color, CFG.fog.density);
```
加上 `mistField`（`§14`）做云雾，但**不是真正的体积雾**——没有光轴穿过雾气产生的丁达尔效应（除了灯笼那点体积光团，`12-env.js:265`，且 low 档关闭）。

**松绑方案**：屏幕空间体积光（god rays / radial blur）或低分辨率体积雾（raymarch 一张 1/4 分辨率深度图）。

**好处**：晨昏时分光柱穿过竹林、雾气里透光——氛围感质变。

**代价**：**2~3 人日**（raymarch 调参 + 性能兜底）｜付费 **0**｜硬件：中高端 GPU；核显需关（与现有 `WITH_VOL` 同策略）。

### 2.7 阴影类型是 PCF（非软阴影）
**现状**（`src/02-scene.js:57`）
```js
renderer.shadowMap.type = THREE.PCFShadowMap;   // r184 已弃用 PCFSoftShadowMap
```

**松绑方案**：用 **VSM（方差阴影）** 或 **PCSS（接触硬化软阴影）**——影子边缘按遮挡距离自然变虚，近处实、远处虚，比 PCF 真实得多。

**好处**：影子不再是"一刀切的硬边"，接触处的虚实过渡更像真实光。

**代价**：**1~2 人日**（VSM 有漏光问题要调）｜付费 **0**｜硬件：VSM 需要额外 blur pass，中等开销。

## 3 · 几何与资产

### 3.1 ⛔ 已拍板（2026-10-03）：**不引入第三方高模，继续全程序化**

老黄 2026-10-03 明确选择"继续全程序化"。本轮据此**只做程序化的呈现效果修复**，
不新增任何外部模型。当初评估出的引入前置条件（留档备查，日后若要重启先逐条解决）：

1. AI 生成的 GLB 常带 `metallicFactor=1` → 低档位无强环境反射时渲染成**黑块**
   （金刚鹦鹉实测：假山顶只看到一个小黑点；修法是挂载时把 `metalness/roughness` 压回区间）；
2. 必须有 **LOD**，且高模不能进 `mergeStatics` 的静态合并桶（会推高 draw calls）；
3. 零 CDN 硬约束 ⇒ 模型必须本地化并用 Draco / KTX2 / Meshopt 压缩；
4. 素材授权（本文"付费"栏写的是"可能需购买授权"）；
5. `sw.js` 的 `GLBS` 与 `src/13-preload.js` 的 `PRELOAD_MANIFEST` 必须同步
   —— 这条现在有门禁了（`probe/preload-manifest-sync.mjs`）。

**明确值得 / 不值得的判断也一并留档**：值得的是"视觉焦点"（立峰太湖石、雕花窗棂）；
不值得的是植被叶（4 万片实例）、人物（剪影路线已拍板，AI 人物落进恐怖谷是本项目血泪史）、
大面积山体/远山（程序化更可控，且远山本就是风格化的层叠剪影）。

### 3.1 · 原评估（2026-09-24 留档，已被上面的决策覆盖）
**现状**：假山 / 建筑 / 植被 / 人物**全部代码生成**；外部资产只有 4 个 GLB（`assets/`）：
```
BananaPlant.glb  267KB   LotusPlant.glb  267KB   Turtle.glb  407KB   koi.glb  208KB   （合计 ≈1.1MB）
```
（几何合并见 `09-lights.js:45` `mergeStatics`，把 draw call 从数百降到几十。）

**为什么要这么设**：这是项目的**立项定位**——"全程序化 + 零 CDN 本地交付"。

**问题（显示效果的上限）**：细节受程序化几何限制——树叶是简单卡片、石头是"扰动球"、没有真雕花 / 真瓦当 / 真太湖石纹理。**近观不够真**。

**松绑方案**：
- **A. 引入高模 GLB**（摄影测量 / 雕刻的太湖石、瓦当、木雕），用 **Draco / KTX2 / Meshopt** 压缩（依赖已在 `package.json`），程序化做远景、高模做近景 **LOD**。
- **B. 只对"视觉焦点"上高模**（如主峰立石、堂前雕花窗），不全面替换。
- **C. 保持全程序化**，用更精细的 SDF / 程序化纹理提升近观。

**好处**：近观质感质变（真石头纹理、真雕花、真瓦当）。

**代价**：时间 **5~10 人日**（找/做素材 + LOD + 压缩管线）｜付费 **素材可能需购买授权**（几百~几千元，视素材来源）｜硬件：高模需 LOD 兜底，否则 draw call / 显存上升。⚠️ **与"全程序化"立项定位冲突，必须老黄拍板**。

### 3.2 程序化贴图分辨率有限
**现状**（`src/01-materials.js`）：石材 / 木纹 / 瓦面等由 canvas 程序化生成，尺寸是各种 `S` / `W×H`（如 `01-materials.js:92` 的 512²）。

**松绑方案**：提高 canvas 分辨率（512→1024/2048）+ 生成 mipmap；或改用**程序化 shader**（无贴图、无限分辨率）。

**好处**：近观纹理更锐利（石材颗粒、木纹、瓦垄）。

**代价**：**0.5~1 人日**｜付费 **0**｜硬件：显存 + 启动期生成耗时上升（当前启动分段里程序化贴图生成本就占一段）。

**好处**：近观更繁茂，且不牺牲远景性能。

### 3.4 折射层只渲"正上方俯视的顶面"
**现状**（`src/05-water.js:136-141`）
```js
refractCam = new THREE.OrthographicCamera(-PBW/2, PBW/2, PBD/2, -PBD/2, 4, 18);
refractCam.position.set(0, 10, 3);      // 正上方垂直俯视
refractCam.layers.set(LAYER_REFRACT);
```
水面下的"透过水看到的东西"是这张正交俯视贴图。**垂直俯视 ⇒ 半浸物的侧面根本进不去**（`MEMORY.md` 已记此取舍）。

**问题**：半浸物（汀步石侧面、岸边石下半截）透过水看时侧面缺失。

**松绑方案**：
- **A. 多角度折射**（侧向补一张）——但多一遍渲染。
- **B. 屏幕空间折射（SSRefraction）**——按主画面深度做折射，半浸物天然正确。
- **C. 半浸物单独做"水下部分"层**——给半浸物额外渲一层侧面。

**好处**：透过水看到的半浸物完整、不失侧面。

**代价**：A **1 人日**（多一遍水下渲染）｜B **2~3 人日**（SSR 在核显上吃力）｜付费 **0**｜硬件：中高端。

## 4 · 物理与仿真（"合理性"限制最集中的一类）

> **总纲**：本项目**没有物理引擎**（`package.json` 里只有 three / playwright / draco / ktx-parse / meshoptimizer / esbuild，**无 cannon / rapier / ammo**）。
> 所有"物理"都是**脚本化近似**：风是顶点位移、水是法线贴图 + 反射 + 折射合成、鱼是动画、灯笼是单摆。
> 这是浏览器实时渲染的合理取舍，但也是"合理性"上限的根源。

### 4.1 风是顶点位移近似，不是流体
**现状**（`src/2b-wind.js`）：三层**离散**调度——L1 风向 16 档（每 12~30s 换一次）、L2 风力 4 档（微风/中风/大风/台风）、L3 在风向坐标系里做顶点位移合成（`addWind` shader）。

**为什么要这么设**（`2b-wind.js:15-17`）：连续随机会让风每秒变向，枝叶来不及完成摆动就被反向 → 眼睛看到的是高频抽搐噪声，不是风。**真实的风是"一段时间的稳定方向 + 偶尔转向"**。

**问题**：不是真流体——**没有涡流、没有空间变化、没有枝叶互相遮挡**；同框里的摆动是"按权重位移"，缺少风的局部性。

**松绑方案**：
- **A. 连续风场**：用 Perlin / Simplex 噪声驱动风向与强度，并加**空间变化**（同一阵风在不同位置有相位差）。
- **B. GPU 风可视化粒子**：把风的流线画出来（艺术向）。
- **C. 真柔体**（布料/枝干用 Obi 类）：**不建议**——浏览器实时跑不动。

**好处**：A 能让风有"涡流感和局部性"，摆动更自然。

**代价**：A **2 人日**（成本低、收益中，性价比高）｜C **10+ 人日 + 硬件要求极高**（不适合浏览器）｜付费 **0**。

---

### 4.2 软渲染下单帧步长被夹在 50ms
**现状**（`src/11-loop.js:556`）
```js
const rawDt = timer.getDelta();        // 真实帧间隔
const dt = Math.min(rawDt, 0.05);      // 仿真钳制在 50ms
```
所有仿真吃**累加的 dt**（`windClock`），不吃墙钟。

**为什么要这么设**：软渲染一帧可能 8.4 秒，不钳制会让相位瞬移。

**问题**：**低帧率下仿真变慢（时间膨胀）**——真机 60fps 无影响，但掉到 20fps 时动画会掉速。

**松绑方案**：**固定步长累积器**（fixed timestep accumulator）——仿真按固定 16.6ms 步进，累加器消化剩余时间，渲染帧做插值。低帧率下仿真速度仍然正确。

**好处**：低帧率下动画速度正确，不掉速。

**代价**：**1 人日**（纯逻辑改动 + 回归）｜付费 **0**｜硬件 **不变**（这是纯正确性修复，不增开销）。

---

### 4.3 水面菲涅尔上限 0.68、折射偏移 ≤0.4m
**现状**（`src/01-materials.js:549-552,606`）
```js
fres = clamp(0.04 + fres * 1.02, 0.0, 0.68);            // 上限 0.90→0.68
ruv += nrm.xz * (0.004 + 0.020 * (1.0 - cosI));          // 折射偏移压着 ~0.4m
```

**为什么要这么设**：不做成镜子（真实园林池水掠射角也只反射六七成天光）；偏移太大池底会被拉花成一片糊。

**松绑方案**：物理正确的 **Schlick 菲涅尔**（按入射角连续变化）+ 更精细的波纹法线贴图。

**好处**：近岸 / 远岸的反射差异正确，水面更真实。

**代价**：**0.5~1 人日**（调参 + 与低档假反射兼容）｜付费 **0**｜硬件不变。

---

### 4.5 锦鲤 / 龟是 GLB 动画，不是游动仿真
**现状**（`src/06-vegetation.js:747`）`new GLTFLoader().load('assets/koi.glb', ...)`——鱼是动画播放，不避障、不响应涟漪。

**松绑方案**：**Boids 群体行为**——分离 / 对齐 / 聚合三力 + 避障（绕石头）+ 响应水面扰动（点水惊鱼）。

**好处**：鱼群有生命感，会绕石、会被人点水惊动，不再是"按轨迹游的模型"。

**代价**：**2~3 人日**｜付费 **0**｜硬件：低（几十条鱼，CPU 计算）。

## 7 · 一句话结论（说人话版）

- **这个项目现在的画质天花板，不是"技术做不到"，而是"为了核显能跑 + 离线交付 + 全程序化，主动砍的"。**
- **想白嫖提升**：先做 GPU 三档细分、固定步长仿真、GTAO 半分辨率——**不花钱、不抬硬件门槛**，中端设备立刻受益。
- **想要质变**：要么上**高模资产**（要钱、要时间、且动摇"全程序化"定位，得你拍板），要么上 **TAA + 级联阴影 + 体积雾**（不要钱但吃工期）。
- **别碰**：真流体 / 柔体物理（浏览器实时跑不动）、改 CDN 在线（丢离线定位）。
