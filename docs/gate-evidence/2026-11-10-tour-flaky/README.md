# 2026-11-10 · 巡游门「走不满 10 站」是量具的采集时长不够（FLAKY）

## 1. 现象
整套门禁里 `probe/tour-guard.mjs` 连续两次红（第 1 次 + 重跑仍红）：

```
第 1 次：✗ 巡游按序走满 10 站 — 0:立峰·云根 → … → 7:远香堂        （停在 7 站）
重跑  ：✗ 巡游按序走满 10 站 — 0:立峰·云根 → … → 8:荷风四面        （停在 8 站）
```

而**逐站落位**这条同类判据两次都合格（`hΔ ≤ 0.012m`、`tgtΔ ≤ 0.05m`，`#6 dy=0.63` 是 polar 允许的抬升）——
说明飞得对、停得对，只是**没走到第 9 站就超时**。

## 2. 定位（三步都只读，没改产品代码）
1. **同一份代码、同一个门，独立重跑 = 全绿**：`01-after-tour-rerun.log` 里 `EXIT=0`，10 站 `0..9` 按序走满，逐站落位全部合格。
2. **每站真实耗时实测**：临时诊断 `probe-tour-rate.mjs.txt`（`?tier=low` 下运行）——
   `FPS 46.09`、`drawCalls 505`、站点间隔 `7.55 / 7.42 / 7.56 / 7.55` ⇒ **7.52s/站**。
   与设计值吻合：飞行 1.4s + 停留 6s = 7.4s（`src/08d-tour.js:555` 注释、`:191 CAM_FLY.dur:1.4`）。
   ⇒ 10 站正常需要 **≈75s**。
3. **为什么整套里只走到 7~8 站**：原采集窗口 `110s`，实际只走 7.5 站 ⇒ 14.7s/站。
   巡游计时吃的是固定步长的仿真步长（`src/00b-fixedstep.js` `maxFrame: 0.1`，单帧最多补 0.1s），
   帧率塌到 5fps 上下时仿真钟只剩墙钟约一半 ⇒ 75s 的巡游要 150s 才走完，110s 窗口自然不够。
   整套连跑时前一门刚关浏览器、机器有余温，正是帧率最容易塌的时刻。

## 3. 处置（判据一个字没动）
`probe/tour-guard.mjs` 改两处，都是**量具的采集条件**，不是判定标准：

- URL 钉 `?tier=low`（与 `probe/smoke.mjs`、`probe/festival-guard.mjs` 同法；项目 2026-10-19 既有定案：双显卡档位漂移 ⇒ 门禁钉 `?tier=`，判据数字不动）。低档实测 46fps、drawCalls 505，余量最大。
- 采集窗口 `110000ms → 160000ms`，注释写明推导（75s × 低帧机器最多 2 倍 = 150s）。
- **没动**：10 站按序、逐站落位阈值（`hΔ<0.05 / tgtΔ<0.30`）、跨墙判据、字幕一一对应。

## 4. 哪条不能当证据
- 「整套里帧率塌到 5fps」是由 14.7s/站**反推**出来的，不是直读；那一轮没抓到 fps。直读的只有独立重跑的 46fps。
- 独立重跑那次门不打印 GPU 行，无法确认落的是哪块卡；但 10 站走满 + 落位全合格本身已足以判定「代码没坏」。
- 本条结论是 **FLAKY + 量具加宽**，不等于「巡游在慢机上体验没问题」：真机上低帧时用户每站仍要等更久，那是观感问题，另算。
