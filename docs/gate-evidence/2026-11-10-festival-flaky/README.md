# 2026-11-10 · 灯会门第④项「最坏帧 1666」单跑不过阈（判定 FLAKY，判据未动）

## 1. 现象
整套 95 道里 `probe/festival-guard.mjs` 红，唯一红项是第④条：

```
✗ ④ 灯会态 draw calls 仍 < 1600（预算没被顶破） — 最坏帧 1666 / 1652 · 连续 60 帧 ·
   帧总量分布 min~med~max = 940~948~1666
```

判据取的是「60 帧里的**最坏帧**」。中位数只有 948，比上限低 652 —— 也就是说**常态离预算还远，红的只是一帧**。

## 2. 定位（只读，没改产品代码）
- 同一份代码、同一个门，**单跑一次 = 全绿**：`ALL PASS（21 项）`，
  ④ 那条变成 `最坏帧 1461 / 上限 1600（余量 139）· min~med~max = 947~947~1461`。
- 两次的**中位数几乎相同**（948 vs 947），差别全在 max（1666 vs 1461，差 205）。
- 这个形态在本门的历史注释里已经写过一次（2026-10-30）：`1522 / 1782 / 1522` 三跑，中位 974 一模一样，只有 max 在跳；
  当时的结论是「采样窗口夹在了水面反射的收尾期」，并在采样前加了「等相机连续 20 帧不动」。
  ⇒ 今天这个 1666 是**同一类形态的再现**，不是场景变重了。

## 3. 处置：只落证据，不动判据
- 本轮**没有**修改 `probe/festival-guard.mjs`，也没有动阈值 1600。
- 为什么不动：现有读数只能证明「单跑是绿的、中位稳定」，**不能指认**那 205 笔增量到底来自哪一趟（水面按需反射 / 开灯会那刻的环境重烘 / 阴影 pass）。
  在指认不出具体来源之前改判据（比如把 max 换成次高值，或改成中位+极差）＝ 拿猜当结论，正是这个项目反复吃亏的地方。
- 已定性为 **FLAKY（整套连跑红、单跑绿）**，与同批的 `tour-guard`、`reel-guard`、`refract-guard`、`aa-progressive`、`hill-guard` 同类。

## 4. 哪条不能当证据 / 下一步
- 不能当证据的：「整套连跑时机器余温导致帧率更低」只是解释方向，**没有直读 fps 支撑**；本轮没抓到那一刻的帧率。
- 下一步（未做，需先有直读）：在同一门里加逐帧增量日志（每次 `composer.render()` 的 calls 与当帧 fps 一起记），
  让最坏帧能指回具体第几帧、那一帧还发生了什么（是否刚触发环境重烘 / 反射整帧更新）。有了这个再决定：
  产品侧摊薄切换成本，还是把判据统计量从 max 换掉。**没有直读之前不改判据。**
