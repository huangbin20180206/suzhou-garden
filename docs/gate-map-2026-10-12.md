## 4. 耦合陷阱与作业铁律

1. **跑链期间不得改 `src/` 或 `probe/`。** 半改状态会被门禁读到，结论既不是改前也不是改后，等于白跑；且下面的 GPU 独占要求也禁止并发编辑。
2. **GPU 探针不得并行。** 每道浏览器门各起一个真 GPU 的 Chromium，并行会互抢显存与 CPU ⇒ 拖慢并**误报**。`verify-all` 是串行执行器，请始终经它跑多门；要手动跑也一次一道。
3. **跑链期间别做观感 / 帧率测试**（同一原因）。
4. **`check` 对 `probe/*.mjs` 零覆盖** —— 改探针只能实跑，别以为绿了就没事。
5. **单门可独立跑**：`node probe/xxx-guard.mjs`。**挑门跑**：`node probe/verify-all.mjs --gates=a,b`；**快门档**：`npm run verify:quick`（该次 12/76，实测 313.6s；现 SUITES 已 78）。
6. **发布前必须跑全量** `npm run verify` —— `verify:quick` 自己的提示语就这么写的。
7. **无 GPU 环境（CI）**：设 `GARDEN_SOFT=1` 走软渲染回退分支（`_harness.mjs` 默认参数是 Windows 的 `--use-angle=d3d11`，Linux runner 上无效）。软渲染约 2.4s/帧，超时要放宽。
8. **端口不冲突**：浏览器探针各自 `listen(0)` 起临时端口，不与常驻的 `npm run serve`（8935）冲突，可同时开着开发服务器。
9. **门禁必须有牙**：几道门自带**负例自检**（`preload-manifest-sync` 4 条变异 + 1 条阳性对照、`plum-guard` 缺陷态负例、`codeonly-unit` 契约双向）。改这些门时不要削弱自检 —— 判据不自证能红，那门就是装饰。
10. **判据要特异**：历史上有过「扫整个目录」导致往 `docs/` 放一篇评审文档就判红的假红案例，也有过「只断言状态数值、不断言画面上看得见」导致「做了但看不见」全绿的假绿案例。改门禁判据时两个方向都要想。
11. **复制品按表达式字符串定位，不按行号**（多 Bot / 多人并行时行号随时位移，本轮已实测踩到）。
